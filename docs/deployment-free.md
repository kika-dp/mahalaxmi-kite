# Free deployment: Neon (database) + Render (API) + Vercel (CRM)

```
iPhones ──────────────────────────────► https://kite-api.onrender.com/api/v1   (Render, free)
                                                │
Browser ─► https://kite-crm.vercel.app ─(proxy /api/* )─┘                  ──► Neon Postgres (free)
           (Vercel, free)
```

The CRM **proxies `/api/*` to Render**, so the browser only ever talks to the Vercel domain. This keeps the CRM's httpOnly sign-in cookie first-party. Without it, browsers drop the cookie because `vercel.app` and `onrender.com` are different sites. The iPhone app calls Render directly.

Everything below was rehearsed locally from a clean copy (Render build + start + migrations + owner bootstrap; Vercel build + proxy + sign-in in Chromium). The live accounts themselves haven't been tested yet.

---

## Know these free-tier limits first (checked Nov 2026)

| Limit | Effect on the shop | What to do |
|---|---|---|
| **Render free sleeps after 15 min without traffic**, and waking can take up to ~1 min ([Render docs](https://render.com/docs/free)) | The first bill or sign-in after a quiet spell can time out on the phone (the app waits 15 s; retrying is safe and never duplicates a bill). | Ping `https://<render-app>.onrender.com/api/v1/health/live` every 10 min with a free monitor (cron-job.org or UptimeRobot). One always-awake service uses ~744 of Render's **750 free hours/month**, so this only works for one service (which is why the CRM is on Vercel). |
| **Render free disk is wiped** on every restart, redeploy or sleep | **Product images disappear.** Bills, stock and everything else live in Neon and are safe. | Skip product images, or move to paid Render, or ask for image storage in the database / a free object store. |
| **Neon free: 1 GB storage**, 100 CU-hours/month, sleeps after 5 min idle and wakes in about a second ([Neon](https://neon.com/faqs/free-plan-limits-and-quotas)) | ~4 KB per bill (measured: 27 MB for 4,738 bills) → roughly 200,000+ bills. | Nothing for now. If storage fills, writes fail (no surprise bills). |
| **Vercel Hobby (free) is for personal, non-commercial use** under Vercel's terms | A shop is commercial use. | Accept the risk, use Vercel Pro, or host the CRM elsewhere (it builds as a normal Next.js app). |
| **Region**: your Neon database is in **us-east-2 (Ohio)** | Each phone ↔ API round trip from India is ~250–300 ms. | Put Render in **Ohio** too, which is already set in `render.yaml`, so API ↔ DB stays fast. For the snappiest app in India, create the Neon project in **Singapore** and set Render's region to `singapore`. |

## Step 1 — Neon (done by you)
You need **two** connection strings from Neon → *Connect*:
- **Pooled** (host contains `-pooler`) → `DATABASE_URL` (used by the running API)
- **Direct** (same but without `-pooler`) → `MIGRATE_DATABASE_URL` (used for migrations)

## Step 2 — Put the code on GitHub
Render and Vercel deploy from a Git repository:
```bash
# create an EMPTY private repo on github.com (no README), then:
cd ~/Documents/Kite-festival
git remote add origin git@github.com:<you>/kite-shop.git
git push -u origin main
```
(`.env` is git-ignored and is never pushed.)

## Step 3 — Prepare the Neon database (from this Mac, once)
With the real connection strings in the repo-root `.env`:
```bash
pnpm build:packages && pnpm --filter api build
pnpm --filter api migration:run           # creates all tables in Neon (uses MIGRATE_DATABASE_URL)
NODE_ENV=production BOOTSTRAP_ADMIN_USERNAME=owner BOOTSTRAP_ADMIN_EMAIL=you@example.com \
  BOOTSTRAP_ADMIN_PASSWORD='Choose#Temp2027' node apps/api/dist/database/seeds/prod-bootstrap.js
```
This creates settings, categories, the season and **one owner account** (you change the password at first sign-in). **Never run `seed:dev` against Neon.** It would create the 12 publicly documented dev accounts on a database reachable from the internet.

## Step 4 — Render (API)
1. render.com → **New → Blueprint** → select the repo. Render reads `render.yaml`.
2. Fill the secret values it asks for:
   - `DATABASE_URL` = Neon **pooled** string
   - `MIGRATE_DATABASE_URL` = Neon **direct** string
   - `CORS_ORIGINS` = your Vercel URL, e.g. `https://kite-crm.vercel.app` (fill after step 5; any placeholder works first)
   - `PUBLIC_API_URL` = the Render URL, e.g. `https://kite-api.onrender.com`

   `JWT_ACCESS_SECRET` is generated by Render automatically.
3. Deploy. Check `https://<render-app>.onrender.com/api/v1/health/ready` → `{"status":"ok","database":"up"}`.
4. Set up the keep-awake ping (see the table above).

## Step 5 — Vercel (CRM)
1. vercel.com → **Add New → Project** → import the repo.
2. **Root Directory: `apps/crm`** (Vercel picks up `apps/crm/vercel.json` for install/build commands).
3. Environment variables:
   - `NEXT_PUBLIC_API_URL` = `/api/v1`
   - `API_PROXY_TARGET` = `https://<render-app>.onrender.com`
4. Deploy, then set Render's `CORS_ORIGINS` to the final Vercel URL and redeploy the API.
5. Open the Vercel URL → sign in as `owner` → set your password → **Shop settings**, **Users & roles** (create each salesperson), **Products**.

## Step 6 — iPhone app
- Expo Go testing: `EXPO_PUBLIC_API_URL=https://<render-app>.onrender.com/api/v1 pnpm dev:mobile`, then scan the QR code.
- Installable builds: put the same URL in `apps/mobile/eas.json` (`preview`/`production`) and run `eas build` (deployment.md §4).

## Backups
Neon offers some point-in-time restore on its plans (check the current free-plan window in Neon's console), but you should also keep your own copies:
```bash
PGDATABASE='<Neon DIRECT connection string>' BACKUP_DIR=~/kite-backups \
  PATH="/opt/homebrew/opt/postgresql@17/bin:$PATH" ./scripts/backup.sh
```
(`pg_dump` must be at least as new as Neon's Postgres; this Mac has version 17.)

## Updating
Push to `main`. Render and Vercel redeploy automatically, and Render applies new database migrations on start.

## Local development after this change
The repo-root `.env` now points **local** runs at Neon (your request). Local `pnpm dev:api` therefore reads and writes the production database. The previous local URL is kept as a comment in `.env`; swap the two lines to work against your local database again. Integration tests are unaffected: they always use `kite_test`.
